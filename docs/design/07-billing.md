## 7.1. 本章の範囲

Phase 0.5（商用リリース）で導入する「組織・有料プラン・権限ロール」の設計を扱う。

**本章で扱う**

- 料金プランの定義と、プランごとの上限（会員アカウント数・プロジェクト数）
- 課金の契約主体としての組織（`organizations` / `organization_members`）
- Stripe 連携（Product / Price / Tax Rate / Checkout / Webhook / Customer Portal）
- 単一の利用権限判定（Entitlement）
- プラン変更・解約・支払い失敗からの復旧
- 無料トライアルと重複防止
- 上限超過時の凍結
- プロジェクト権限ロール（管理者 / 編集者 / 閲覧者）とロール付き招待

**本章で扱わないもの**

| 項目 | 扱う場所 |
|---|---|
| テーブルの物理定義（型・制約・インデックス） | 章2 §2.4 |
| エンドポイントの詳細仕様 | 章3 §3.6 |

## 7.2. プラン定義

### 7.2.1. プラン一覧（PRD §4.1.12b の物理化）

| plan_code | 表示名 | 月額（税込） | 会員アカウント上限 | プロジェクト数上限 | トライアル | Stripe 連携 |
|---|---|---:|---:|---:|---:|---|
| `free` | Free | 0 円 | 1 | 2 | なし | **しない** |
| `personal` | Personal | 980 円 | 1 | 10 | 120 時間 | する |
| `team` | Team | 9,800 円 | 5 | 無制限 | 120 時間 | する |
| `enterprise` | Enterprise | 個別見積 | 個別 | 無制限 | なし | **しない**（Phase 1 以降） |

**確定事項**

- プランの正式名称は **「Team」**（"Teams" ではない）。実装・UI・DB・ドキュメントすべてで統一する
- Free は Stripe と一切連携しない。Customer も Subscription も作らず、TRAKON DB の状態のみで管理する
- Team の 5 名上限は **Stripe の quantity ではなく TRAKON 側で判定**する。Checkout の `quantity` は常に 1
- 課金の人数カウント対象は「TRAKON 上でプロジェクトを設計・管理する会員アカウント」。**共有リンクから参加する非会員は含めない**

### 7.2.2. 実装配置

プラン定数は `packages/shared/src/constants/billing.ts` に置き、FE / BE で共用する。

```
BILLING_PLAN_CODES  : ['free', 'personal', 'team', 'enterprise']
BILLING_PLANS       : plan_code -> { label, monthlyPriceJpyIncTax, seatLimit, projectLimit, trialHours, stripeManaged }
SUBSCRIPTION_STATUSES
PAST_DUE_GRACE_DAYS = 7
TRIAL_PERIOD_DAYS   = 5   // = 120 時間
```

> **Price ID は shared に置かない。** 本番とテストで値が異なり、混在させると事故になるため環境変数のみで扱う（§7.3.3）。

### 7.2.3. 名前衝突への対処（重要）

TRAKON では `Plan` が既に**「予定（スケジュール）」**を指す物理テーブル名・ドメイン用語として占有されている（章2 §2.4.5）。課金側で `Plan` を単独で使うと、`plans` テーブル・`PlanDTO`・`features/plans/**` と衝突する。

| 概念 | 採用名 | 禁止 |
|---|---|---|
| 課金プラン種別 | `BillingPlanCode` / `BILLING_PLANS` / 列名 `plan_code` | `Plan` / `PlanType` |
| 契約 | `BillingSubscription` / `billing_subscriptions` | 単独の `Subscription` |
| BE の配置 | `server/services/billing/*` | `services/plans.ts` への追記 |
| FE の配置 | `src/features/billing/*` | `features/plans/` |

## 7.3. 組織モデルと Stripe リソース

### 7.3.1. 契約主体は組織

```
users ──< organization_members >── organizations ──|| billing_subscriptions
                                        │
                                        └──< projects
```

- ユーザー登録（プロフィール作成）時に、本人をオーナーとする**個人組織を自動作成**する
- Personal も「会員 1 名の組織」として扱い、Personal と Team でデータモデルを分けない
- **プランは `organizations` に持たせない**。契約情報の唯一の正は `billing_subscriptions`。組織側にもプラン列を置くと必ず不整合を起こす
- Stripe の Customer は請求主体に紐づける。本設計では **Personal / Team ともに組織へ紐づける**（Personal は「会員 1 名の組織」なので、仕様書 §8.1 の「Personal は本人に紐づける」と実質同一であり、プラン変更時に Customer を作り直さずに済む）

### 7.3.2. 座席（会員アカウント数）の数え方

```
座席消費数 = 有効な organization_members の件数
           + 未受諾かつ有効期限内の invitations の件数
```

**招待中も座席を消費する。** これを入れないと、招待を大量に送ってから一斉に受諾させることで上限を超えられてしまう。招待を取り消せば座席は解放される。

### 7.3.3. Stripe Product / Price

Product は Personal / Team それぞれに 1 件ずつ、計 2 件。実装で参照する有効な月額 Price は各 1 件。

| 項目 | 値の管理場所 |
|---|---|
| Personal 月額 Price ID | 環境変数 `STRIPE_PERSONAL_MONTHLY_PRICE_ID` |
| Team 月額 Price ID | 環境変数 `STRIPE_TEAM_MONTHLY_PRICE_ID` |
| 消費税の手動 Tax Rate ID | 環境変数 `STRIPE_JP_TAX_RATE_ID` |
| Customer Portal の構成 ID | 環境変数 `STRIPE_PORTAL_CONFIGURATION_ID` |

**確定事項**

- テスト環境と本番環境で Product / Price / Tax Rate / Webhook の ID は**すべて別値**。テスト用に本番 ID を流用しない
- 過去に作られた誤り Price・アーカイブ済み Price は使用禁止。**該当 ID をソースコードに書かない**（誤参照を防ぐため、値は `docs/operations.md` の Runbook にのみ記載する）
- Free / Enterprise は Stripe 上に Product / Price を作らない

### 7.3.4. 税処理

- 980 円 / 9,800 円は**税込価格**
- Stripe Tax（自動税計算）は**使用しない**（`automatic_tax.enabled = false`）
- Price は `tax_behavior = inclusive`（税込）で作成する
- JPY はゼロデシマル通貨のため、金額は整数の `unit_amount`（980 / 9800）で指定する
- 請求書上に消費税の内訳を表示するため、Checkout の `subscription_data.default_tax_rates` に手動 Tax Rate（日本国内向け消費税 10%・内税）を指定する
- Checkout では **`managed_payments.enabled = false` を明示的に渡す**。Stripe アカウントの既定で Managed Payments が有効だと Stripe が税を代行する前提になり、`automatic_tax.enabled = true` が必須になる。本設計は税込 Price + 手動 Tax Rate なので噛み合わず、**Checkout Session の作成自体が拒否される**。ダッシュボードの既定に依存しないよう、リクエスト側で無効化する（`STRIPE_PORTAL_CONFIGURATION_ID` を明示指定するのと同じ理由）

> 自動税計算を使わないことと、内訳表示のために手動 Tax Rate を付与することは両立する。手動 Tax Rate は税込価格の内訳を示すためのものであり、課金総額を変えるものではない。

> **実装前の確認事項**：各 Price の `tax_behavior` が実際に `inclusive` であることは、Stripe ダッシュボードの画面上では確認できない。実装前に必ず Stripe API（Price 取得）で実値を確認する。

## 7.4. Checkout

対象は Personal / Team のみ。Free は Checkout を使わない。Stripe のホスト型 Checkout を使用する。

### 7.4.1. パラメータ

```
mode                      = 'subscription'
line_items                = [{ price: <PRICE_ID>, quantity: 1 }]
automatic_tax             = { enabled: false }
payment_method_collection = 'always'
subscription_data = {
  trial_period_days : 5,                          // = 120 時間
  default_tax_rates : [STRIPE_JP_TAX_RATE_ID],
  metadata          : { user_id, organization_id, plan_code, checkout_attempt_id },
}
metadata   = { user_id, organization_id, plan_code, checkout_attempt_id }
customer   = 既存の顧客IDがあれば再利用、なければ Checkout 時に新規作成
success_url = {APP_URL}/settings/billing?checkout=success&session_id={CHECKOUT_SESSION_ID}
cancel_url  = {APP_URL}/settings/billing?checkout=canceled
```

**確定事項**

- `quantity` は常に 1（Team の上限は TRAKON 側で判定するため、Stripe の数量課金は行わない）
- トライアルは `trial_period_days = 5` で指定する。**`trial_end` は使わない** — Checkout Session 作成時刻から実際の申込完了までの時間差だけトライアルが短縮されてしまうため
- `payment_method_collection = 'always'`。トライアル開始時点でもカード登録を必須とする
- トライアル対象外と判定された場合は `trial_period_days` を付与せず、その旨を申込前に画面で明示する

### 7.4.2. success URL の扱い（最重要）

**Checkout の success URL へ遷移したことのみをもって有料権限を付与してはならない**（PRD FR-BILL-05 / SR-BILL-03）。

`/settings/billing?checkout=success` では「反映待ち」を表示し、契約状態を取得する API をポーリングする。状態が確定した時点で初めて有料機能が有効になる。

この実装を省くと「決済したのに反映されない」という問い合わせに直結するため、UX 上も必須である。

## 7.5. Webhook

### 7.5.1. エンドポイントと認可

```
POST /api/v1/stripe/webhook   認証なし・署名検証で認可する
```

TRAKON の 3 層認可（認証 → プロジェクト参加 → ロール）に当てはまらない**唯一の例外**である。章3 §3.2.4 / §3.3 にもその旨を明記する。

**生ボディの取得**：`api/index.ts` が Hono の Web ハンドラを名前付き HTTP メソッド export として公開しているため、Vercel が生成した Web 標準 `Request` がそのまま Hono に渡る。したがってボディは無改変で取得できる。

> ⚠️ このルートでは **JSON パースを先に行ってはならない**。ボディが消費されると署名検証ができなくなる。

### 7.5.2. 購読イベントと処理

| イベント | 処理 |
|---|---|
| `checkout.session.completed` | metadata から組織を解決し、顧客 ID を確定。トライアル利用履歴を記録。**ここでは plan_code を昇格しない** |
| `customer.subscription.created` / `updated` | 契約の現在値を取得し直してスナップショットを適用。**Team の Price かつ有効状態のときに初めて `plan_code` を team へ昇格** |
| `customer.subscription.deleted` | 解約済みへ。解約完了メール |
| `customer.subscription.trial_will_end` | トライアル終了間近の通知メール |
| `invoice.paid` | 有効状態へ復帰、猶予期限をクリア。**保留中のプラン変更があればここで確定**（§7.7.1） |
| `invoice.payment_failed` | 支払遅延へ。猶予期限（+7 日）を設定。通知メール |
| `invoice.payment_action_required` | 追加認証が必要。Portal 誘導メール |
| `invoice.updated` | 請求書情報のみ更新 |

### 7.5.3. 処理順序（冪等性・順序逆転・トランザクション）

```
1. 署名検証（生ボディ + 署名ヘッダ + Webhook Secret）
   → 失敗は 400。Stripe は再送しない
2. 受信台帳へ INSERT（イベント ID に一意制約、衝突時は何もしない）
   → 既に存在すれば処理済みとみなし即 200 を返す        ← 冪等性
3. 契約系イベントは受信ペイロードを信じず、Stripe API から現在値を取得し直す
   → 順序逆転が構造的に消える（後述）
   ★ この外部 API 呼び出しはトランザクションの外で行う
4. 請求書系イベントのみ、最終反映イベント時刻より古いものをスキップ扱いにする
5. トランザクションで「契約状態の更新 + 監査ログ + 受信台帳の処理済み記録」を書く
6. コミット後に通知メールを 1 通だけ送る（失敗は握りつぶす）
7. 200 を返す。内部エラーは 500 を返して Stripe に再送させる（冪等なので安全）
```

**なぜ「取得し直す」のか**：Stripe のイベント発生時刻は秒精度であり、同一秒内に発生した created / updated の前後関係は時刻比較では判別できない。ペイロードの中身ではなく**その時点の真の状態**を取りに行くことで、どの順で届いても最終状態が正しくなる。

**メール送信をトランザクション外・コミット後にする理由**：メール送信の失敗で 500 を返すと、Stripe が再送し続けて無限ループになる。

### 7.5.4. 実行環境上の制約

| 制約 | 対処 |
|---|---|
| Vercel 上では DB 接続数が 1 に制限される（章1 §1.2、`packages/db`） | **Stripe API 呼び出しをトランザクションの中に入れない**。1 本しかない接続を数百 ms 占有すると他のリクエストがプールタイムアウトする |
| インタラクティブトランザクションの既定タイムアウトは 5 秒 | Webhook 処理では明示的に 10 秒へ引き上げる |
| Stripe は約 20 秒でタイムアウトして再送する | 処理を「検証 → 台帳 INSERT → 現在値取得 1 回 → トランザクション → 200」に限定する |

## 7.6. 単一の利用権限判定（Entitlement）

### 7.6.1. 原則

**契約状態単体で権限を判定してはならない**（PRD FR-BILL-06）。以下 5 要素を組み合わせた**単一の判定関数**を実装し、アプリケーション全体でこれを共用する。

1. `plan_code`
2. 契約状態（`status`）
3. 解約予約（`cancel_at_period_end`）と請求期間終了日
4. 支払猶予期限
5. プランごとの会員アカウント数・プロジェクト数の上限

配置：`packages/shared/src/domain/entitlement.ts`。**Date / DB / Prisma に依存しない純関数**とし、`domain/ballHolder.ts` と同じ流儀で実装する。

### 7.6.2. 入出力

| 入力 | 出力 |
|---|---|
| `planCode` / `status` / `cancelAtPeriodEnd` / `currentPeriodEnd` / `gracePeriodEndsAt` / `seatCount` / `projectCount` / `now` | `level`（`full` / `read_only` / `blocked`）／`reason`／**`effectivePlanCode`**／`limits`／`usage`／`over`／`canCreateProject`／`canInviteMember`／`graceEndsAt`／`message` |

`effectivePlanCode` は「契約状態を踏まえた実効プラン」。解約済み・手続き未完了などでは `free` に落ちる。**上限判定には必ず実効プランを使う。**

### 7.6.3. 判定規則

| 契約状態 | level | 実効プラン |
|---|---|---|
| `trialing` / `active` | `full` | 契約プラン |
| `past_due` かつ猶予期限内 | `full`（理由：猶予中） | 契約プラン |
| `past_due` かつ猶予切れ | `read_only` | 契約プラン |
| `unpaid` | `read_only` | 契約プラン |
| `paused` | `read_only` | 契約プラン |
| `canceled` | 下記 free 判定へ | `free` |
| `incomplete` / `incomplete_expired` | 下記 free 判定へ | `free` |
| `none`（Stripe 未連携＝ Free） | 下記 free 判定へ | `free` |

加えて：

- 解約予約あり かつ 請求期間終了前 → `full`（理由：解約予定）。**期間終了までは有料権限を維持する**
- 解約予約あり かつ 請求期間終了後 → 実効プランを `free` に落とす。**Webhook 遅延の保険**。時刻だけを根拠に昇格はしないが、降格はする（安全側）
- 実効プランの上限を超えている場合、全体を `read_only` にはせず、**超過分のプロジェクトのみを凍結する**（§7.11）

### 7.6.4. FE と BE の分担

BE が判定結果を DTO として返し、**FE はそれをそのまま表示に使う（FE で再計算しない）**。二重実装は必ずずれるため。判定関数自体は `packages/shared` にあるので FE からも import でき、楽観的 UI に使うことはできる。

## 7.7. プラン変更・解約

### 7.7.1. Personal → Team（即時）

- 残期間分の差額を日割りで請求する（`proration_behavior = 'always_invoice'`）
- `payment_behavior = 'pending_if_incomplete'` を指定し、追加請求の決済が完了するまで契約を保留状態とする
- DB には **保留中のプラン変更**として記録するのみ。**追加請求の成功を Webhook（`invoice.paid` または有効状態の契約更新）で確認するまで Team 権限を付与しない**
- 支払い失敗時は Team 権限を先付けしない

### 7.7.2. Team → Personal（次回更新時）

- 即時変更としない。次回更新時に適用する
- 返金は行わない
- **前提条件**：会員アカウントが 1 名以下、かつプロジェクト数が 10 件以下
- 条件を満たさない場合はダウングレードを受け付けず、**超過しているメンバー・プロジェクトを画面上に列挙して整理を案内する**

### 7.7.3. 解約

- 請求期間終了時に解約する予約を設定する（`cancel_at_period_end = true`）
- 原則として返金は行わない
- 期間終了後に Free（または制限状態）へ移行する
- 期間終了前であれば解約を取り消せる

> **【確定】解約時にプロジェクトやメンバーを削除してはならない。** Free の上限を超えている場合の編集制限は、TRAKON のアプリケーションロジック（§7.11 の凍結）で実装する。Stripe 側では制御しない。
>
> 本設計では凍結を「保存された状態」ではなく「都度の計算」として表現するため、**そもそも削除処理がコード上に存在しない**。これが要件を実装レベルで担保する。

## 7.8. Customer Portal

| MVP で許可する機能 | MVP で無効化する機能 |
|---|---|
| 支払方法の変更 | **プラン変更** |
| 請求書・領収情報の閲覧 | 数量（quantity）の変更 |
| 解約 | |

**プラン変更を Portal 上で無効化する理由**：トライアルの扱い、日割り請求、Team の会員数条件、Personal のプロジェクト数条件を、いずれも TRAKON 側で確認する必要がある。Portal 単独でのプラン変更を許すと、これらの条件確認をバイパスしてしまう。

**Portal Session URL は保存せず、アクセスの都度サーバー側で生成する**（PRD SR-BILL-07）。監査ログにも記録しない。

プラン変更の無効化は Stripe の Portal Configuration 側の設定であるため、**構成 ID を環境変数で明示指定する**。ダッシュボードの既定構成に依存しない。

## 7.9. 無料トライアルと重複防止

### 7.9.1. トライアル仕様

- Personal / Team ともに、契約開始時刻から **120 時間**
- 暦日の「5 日間」ではなく時間単位で厳密に管理する。Stripe における 5 日間は 5 × 24 時間 = 120 時間として扱われるため、`trial_period_days = 5` が事業要件と一致する
- 120 時間後にトライアルが終了し、Stripe が初回請求書を生成して決済処理を開始する（トライアル終了時刻と実際の課金時刻が完全に同時とは限らない）
- Free にはトライアルの概念自体が存在しない

### 7.9.2. 重複防止の判定

Stripe の標準機能だけでは重複トライアルを完全には防げないため、TRAKON 側で履歴を保持して判定する。

| 判定キー | 扱い |
|---|---|
| ユーザー ID | **ハード拒否** |
| 正規化メールアドレス | **ハード拒否** |
| 組織 ID | **ハード拒否** |
| 過去の決済顧客 ID | **ハード拒否** |
| メールドメイン | **記録のみ**（拒否しない） |
| カード識別子（fingerprint） | **保存も参照もしない** |

> **【確定】法人カードの共有による誤判定があり得るため、カード識別子のみを根拠に自動拒否してはならない。** 本設計では PCI 上の観点も踏まえ、カード識別子を保存すること自体を行わない。

### 7.9.3. 手動解除

誤判定に備え、運営がトライアル履歴を手動で解除できる必要がある。**Phase 0.5 では管理画面・管理 API を作らず、DB の直接操作と運用手順（Runbook）で対応する。**

- 解除は履歴行に「解除日時・解除理由・解除実施者」を記録する形で行う（行を削除しない）
- 手順は `docs/operations.md` に Runbook として整備する
- 解除操作は監査ログにも 1 行残す

## 7.10. 支払い失敗と復旧

### 7.10.1. 再試行設定（Stripe 本番設定として確定済み）

- 支払い失敗後、**7 日間で最大 4 回**まで再試行する
- 7 日間の再試行後もすべて失敗した場合、契約は `unpaid` へ移行する
- カード決済失敗時の Stripe 自動メール送信は有効になっている

### 7.10.2. 復旧フロー

```
1. invoice.payment_failed を受信
2. 支払遅延（past_due）として保存し、猶予期限を「初回失敗 + 7 日」に設定する
   ※ 既に猶予期限が入っている場合は上書きしない（再試行のたびに猶予が延びるのを防ぐ）
3. アプリ内警告バナーとメール通知
4. ユーザーが Customer Portal でカード情報を変更
5. invoice.paid の受信で有効状態へ復帰し、猶予期限をクリア
6. 7 日間の再試行後に unpaid へ移行した場合は、新規作成・編集操作を停止する（閲覧は可能）
7. 再契約時は、既存の顧客および保存データを再利用する
```

**猶予期間中は通常どおり利用できる**（PRD FR-BILL-10）。支払いの一時的な失敗で即座に業務が止まると、TRAKON が進行を止める側になってしまうため。

## 7.11. 上限と凍結

### 7.11.1. 上限のチェック地点

| 地点 | チェック内容 |
|---|---|
| プロジェクト作成 | プロジェクト数上限 |
| 招待の作成 | 座席上限 |
| 招待の受諾 | 座席上限の**再**チェック（作成時に空きがあっても受諾時に満席になりうる） |
| プラン変更（Team → Personal） | 座席数・プロジェクト数の両方 |
| 書き込み系エンドポイント全般 | 利用権限レベルと凍結状態 |

### 7.11.2. 凍結の決定ルール

**上限超過分は削除せず、「新規編集不可・閲覧のみ」で凍結する。** ユーザーがどのプロジェクトを維持するか選べるまで凍結状態を保つ。

決定的なルール（`packages/shared/src/domain/projectFreeze.ts`）：

1. アーカイブ済みプロジェクトは対象外（元から編集不可でカウント外）。**＝アーカイブが枠を空ける正規の動線**
2. プロジェクト数上限が無制限なら全件が有効
3. 並び順「維持指定が新しい順 → 作成が古い順 → ID 順」の先頭から上限件数までが有効、残りが凍結

### 7.11.3. 凍結状態を保存しない

凍結は**都度計算**とし、DB にフラグを持たない。理由：

- プラン変更・Webhook の遅延・アーカイブ操作と自動的に整合する
- フラグを更新するための定期バッチが不要になる
- 「凍結フラグは立っているが実はもう上限内」という不整合が原理的に発生しない

ユーザーによる維持対象の選び直しは、プロジェクトに「維持指定日時」を記録することで表現する。

### 7.11.4. エラーの返し方

TRAKON は認可失敗を 404 に集約している（章3 §3.2.4）。**課金・上限・凍結のエラーはこれに含めない。**

| 事象 | ステータス | 理由 |
|---|---|---|
| プロジェクトに参加していない | 404 | 存在の秘匿が必要（既存方針） |
| プロジェクト数上限に到達 | 409 | 秘匿の必要がなく、復旧手段を案内する必要がある |
| 座席上限に到達 | 409 | 同上 |
| ダウングレード条件を満たさない | 409 | 超過しているメンバー・プロジェクトを詳細として返す |
| 契約が閲覧のみ状態 | 403 | 同上 |
| プロジェクトが凍結中 | 403 | 同上 |

404 に混ぜると、フロントエンドが「存在しません」と表示してしまい、ユーザーが復旧手段にたどり着けない。

**ミドルウェアの順序を「参加確認 → 書き込み可否（課金・凍結）→ ロール」に固定する。** これにより、課金エラーはプロジェクト参加者にしか見えない。

## 7.12. プロジェクト権限ロール

### 7.12.1. ロールの定義

`project_members.role_type` に **`admin`（管理者）／`editor`（編集者）／`viewer`（閲覧者）** を持たせる。

**これが操作権限の唯一の根拠である。** `member_type`（区分：production / client / partner）と `job_title`（職種）は表示専用で、権限には一切影響しない。

> **v1.1 からの変更**：章5 §5.4.2 の「Phase 0 は `member_type='production'` かつ `users.id = projects.created_by` から director を導出する」という簡易ロールは **v1.2 で撤回**した。

**例外**：プロジェクト作成者は `role_type` の値によらず常に管理者として扱う。自分のプロジェクトから締め出されることを防ぐ最終防衛線である（PRD FR-ROLE-04）。

### 7.12.2. ロール別操作マトリクス

配置：`packages/shared/src/domain/projectRole.ts`。**「操作 → 許可ロール」の向き**で定義する（操作を追加したときにロールの宣言を強制するため）。

| 操作 | admin | editor | viewer |
|---|:---:|:---:|:---:|
| `project.view` / `share_link.view` | ○ | ○ | ○ |
| `project.update` / `project.archive` | ○ | × | × |
| `item.create` / `item.update` / `item.delete` | ○ | × | × |
| `plan.create` / `plan.update` / `plan.delete` | ○ | ○ | × |
| `plan.complete`（確認依頼・承認・差し戻し・各取り消し） | ○ | ○ | ○ |
| **`plan.toss`（TOSS・TOSS 取り消し）** | **○** | **×** | **×** |
| `member.create` / `member.update` / `member.remove` / `member.invite` | ○ | × | × |
| `share_link.create` / `share_link.revoke` | ○ | × | × |
| `comment.create`（Phase 1。定義のみ） | ○ | ○ | ○ |

**ボール操作の 2 段判定**

```
1. ロールが操作を許可しているか
2. 管理者なら通す（Ball Holder でなくても可）
3. それ以外は Ball Holder 本人であること
```

### 7.12.3. 権限メモからの読み替え（設計判断）

| # | 読み替え | 理由 |
|---|---|---|
| 1 | 「タスク完了」を `plan.complete` **1 アクション**に集約し、確認依頼・承認・差し戻し・各取り消しをすべて含める | 承認者が閲覧者のときに承認だけ許して確認依頼を禁じると、**確認待ちのまま永久に進行不能**になる。完了フローは分割できない |
| 2 | TOSS 取り消しを `plan.toss`（管理者のみ）に含める | TOSS の裏返しであり、権限を分ける理由がない（Phase 0 実装ではノーチェックだった） |
| 3 | 「プロジェクト追加」は組織の会員なら可、「プロジェクト削除」はアーカイブとして扱う | ロールはプロジェクト単位の概念であり、そのプロジェクトのロールでプロジェクト新規作成を制御することはできない。物理削除の API は Phase 0 時点で存在しない |
| 4 | 「コメント書ける」は定義のみ置き、実装しない | コメント機能自体が Phase 1（章2 §2.3.2） |

### 7.12.4. TOSS を管理者限定にすることの副作用（記録）

TOSS を管理者のみに限定すると、担当者が自分でボールを次工程へ渡せなくなり、**管理者が進行のボトルネックになりうる**。これは TRAKON の中心概念「ボールを前へ動かす」に直接影響する。

この点を認識した上で、権限メモに忠実な運用を優先して管理者限定とした（PRD §9.4 の設計判断メモ、基本原則 第十六条「例外は記録される」）。

**将来この方針を見直す場合に備え、ロール別操作マトリクスを `packages/shared` の単一テーブルに集約する。** ミドルウェア・サービス層・フロントエンドはすべてこの表を参照するため、方針変更は 1 箇所の修正で完了する。

### 7.12.5. ロール付き招待

Phase 0 では**招待の受諾側のみが実装されており、招待の作成・送信は未実装**だった。Phase 0.5 でこれを完成させる。

```
1. 管理者が「招待を送る」からメール・表示名・区分・職種・ロールを指定
2. 座席上限を検証
3. 参加者行を作成（または既存の担当者行にメールを付与）
4. ワンタイムトークンを生成し、招待を作成（ロール・組織・招待者を記録）
5. 招待メールを送信
6. 受諾時：メール一致を検証 → 参加者行にユーザーを紐付け → 指定ロールを付与
          → 組織の会員として追加（座席を消費）→ 座席上限を再チェック
```

**プロジェクトの管理者を 0 名にすることはできない**（PRD FR-ROLE-03）。最後の管理者の降格・削除は API 側で拒否し、UI 側でも操作を無効化する。

## 7.13. 議論ポイントの確定結果

| # | 論点 | 確定内容 | 判断理由 |
|---|---|---|---|
| 1 | 課金の契約主体をどう持つか | **`organizations` を新設**し、Phase 2 予定を前倒しで最小実装する | Stripe 仕様書が Team の請求主体を組織と想定しており、`projects.organization_id` の空カラムも既に先付けされていた。ユーザー直付けにしても実質は組織の別名であり、Phase 2 で再移行が発生する |
| 2 | プランをどこに持つか | **`billing_subscriptions` の 1 箇所のみ**。`organizations` にプラン列を置かない | 二重管理は必ず不整合を起こす。PRD v1.2 の `organizations.plan_type` は撤回 |
| 3 | ロールとボール操作の関係 | **権限メモどおり厳密に。TOSS は管理者のみ** | 事業判断。副作用は §7.12.4 に記録し、変更容易な構造にする |
| 4 | ロールの backfill 方針 | プロジェクト作成者**および進行責任者**を管理者、残りを編集者 | 作成者だけを管理者にすると、「作成者以外が進行責任者」のプロジェクトで **TOSS を実行できる人が誰もいなくなる** |
| 5 | 区分（client）を閲覧者に降格するか | **しない** | 既存データでクライアントが承認者になっている場合に承認不能となる。降格は UI から明示的に行う |
| 6 | 既存ユーザーの移行措置 | **設けない**（クリーンスタート） | 本番実利用者がいない前提。救済措置のための猶予フィールドとバッチを持ち込まない |
| 7 | Enterprise の扱い | **Phase 0.5 のスコープ外**。`plan_code` の値としてのみ定義 | 直近で必要なのは Personal / Team。契約管理カラムを先に入れても運用が伴わない |
| 8 | トライアル手動解除の手段 | **Runbook + DB 直接操作**。管理画面・管理 API は作らない | 問い合わせ頻度が低いうちは十分。実装量を課金本体に集中させる |
| 9 | 凍結状態を保存するか | **保存せず都度計算** | プラン変更・Webhook 遅延・アーカイブと自動整合し、定期バッチが不要になる |
| 10 | 課金エラーを 404 に集約するか | **しない**（409 / 403 + 専用コード） | 404 に混ぜると復旧手段を提示できない。秘匿の必要もない |
| 11 | Webhook の順序逆転対策 | イベント時刻の比較ではなく、**Stripe から現在値を取得し直す** | イベント発生時刻は秒精度で、同一秒内の前後関係を判別できない |
| 12 | Customer Portal でのプラン変更 | **無効化する** | トライアル・日割り・人数/件数条件の確認をバイパスさせないため（Stripe 仕様書 §12.2 の【確定】） |
